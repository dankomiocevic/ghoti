Overview

Ghoti is a single-binary, in-memory server for small pieces of shared state that a fleet of services needs to agree on: a rate limit, a lease, a counter, a signal.

Getting started →Install, verify, first run. Protocol →Commands, framing, retries. Slot reference →Every slot kind and its options. Error codes →What each e response means.

What Ghoti is#

A Ghoti server exposes 1000 numbered slots, 000 to 999. You decide in config.yaml which slots exist and what kind each one is. Clients read and write slots with a plain-text protocol over TCP, or over HTTP. Each slot kind has a fixed behaviour:

KindWhat it doesStatus
simple_memoryHolds a value of up to 36 bytes.Implemented
timeout_memoryA value with an owner: only the connection that last wrote it can write again, until the owner's timeout expires.Implemented
token_bucketHands out tokens refilled every period.Implemented
leaky_bucketAccepts a request if the bucket has room, leaking one token every refresh_rate ms.Implemented
tickerAn integer that counts down by one every refresh_rate ms until it reaches zero.Implemented
atomicA counter that increments on every read.Implemented
broadcastA write is pushed to every connected client.Implemented
multicastA write is pushed to the clients that subscribed to the slot.Implemented
Random signal propagationA write delivered to one subscriber chosen at random.Planned

Around the slots Ghoti has:

  • Three transports: standard TCP (the default), telnet, and http with Server-Sent Events for broadcast slots. See Transports.
  • Optional users with per-slot read and write permissions. See Authentication.
  • An optional Prometheus endpoint and a connection cap. See Operations.
  • Leader election between several nodes, without replication. Experimental See Cluster.

What Ghoti is not#

  • Not a database or a durable store. Nothing is written to disk. A restart empties every slot, and a newly elected cluster leader starts empty.
  • Not a message queue. Broadcast and multicast deliver at most once, with no retries and no backlog for clients that were not connected.
  • Not encrypted. No listener supports TLS, and the p login command sends the password in cleartext. Terminate TLS in a load balancer or reverse proxy, or keep traffic on a trusted network. See SECURITY.md.
  • Not a consensus system. Clustering elects a leader with the bully algorithm. There is no quorum and no replication, and split-brain is possible under network partitions.

Guarantees at a glance#

TopicWhat Ghoti does
DurabilityNone. All state is in memory and is lost on restart.
Ordering on one connectionResponses come back in the order the commands were sent. Async events never appear in the middle of a response.
Ordering across connectionsNo guarantee.
Requests in flightOne per connection. Send a command, wait for its response, then send the next.
Event deliveryAt most once. One attempt per client and no retries. The writer receives a received/sent/errors summary.
Lease ownershipTied to the TCP connection. It survives a dropped connection until the timeout expires and is forgotten on restart.
ValuesOpaque byte strings of at most 36 bytes, returned exactly as written.
Transport securityNone built in. Bring your own TLS termination.
High availabilityExperimental Leader election only. Followers answer NOT_LEADER and do not redirect.

Performance#

On a 2-core, 1 GiB AWS t4g.micro, Ghoti v0.3.0 answered with a 0.29 ms median round trip on one connection, served over 127,000 requests per second with 100 connections, and spent 7.6 µs on average inside the server per memory read. See Benchmarks for the method, every result and how to reproduce them.

When it fits#

Ghoti fits state that is cheap to lose and expensive to coordinate: a fleet-wide rate limit, a lease that picks one active worker, a counter for distinct numbers, or a push signal such as "reload the configuration". If the overall system must keep working when Ghoti is down, possibly degraded, Ghoti is a good fit. If losing the data is not acceptable, use a durable store instead.
